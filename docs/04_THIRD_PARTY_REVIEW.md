# 04. 第三者客観レビュー & リスク分析書 (Third-Party Architecture & UX Review)

本資料は、シニアソフトウェアアーキテクト、Chrome拡張機能スペシャリスト、UI/UXデザイナーの3つの視点から、本計画（`01`〜`03`）を客観的・批判的に精査し、**「予期せぬ落とし穴」「仕様の甘さ」「実現上のリスク」**を洗い出し、事前に対策を定義したレビューレポートです。

---

## 1. 総合評価サマリー

| 評価項目 | 判定 | 概要 |
| :--- | :---: | :--- |
| **技術的実現可能性 (Feasibility)** | **A (極めて高い)** | Manifest V3 および Side Panel API で問題なく実現可能。オープンソースの選定も妥当。 |
| **セキュリティ・規約準拠 (Compliance)** | **A (問題なし)** | ローカル完結型であり、CSPやChrome Web Storeのプライバシーポリシー審査にも引っかかりにくい。 |
| **UX・操作性の親和性 (Usability)** | **B (注意が必要)** | **「狭いサイドパネル」と「広大なマインドマップ」の物理的相性の悪さ**をどう解決するかが最大の壁。 |
| **データ完全性・安定性 (Reliability)** | **B+ (対策必須)** | サイドパネルとフルタブの同時編集時の競合、およびストレージ容量の限界。 |

**総合判定: 【条件付き Go】**  
以下に指摘する「4つの重大な問題点」について、あらかじめ対策を仕様に織り込んでおくことを条件に、プロジェクトの着手を推奨します。

---

## 2. 洗い出された問題点・リスクと具体的対策

### 【問題点 1】狭いサイドパネルにおける「マインドマップの可読性崩壊」問題
* **リスク内容**:
  * サイドパネルは通常「横幅 300px〜450px」程度です。
  * 一般的なマインドマップ（中心から左右放射状に広がる形式）をそのまま配置すると、2階層目を作った時点で左右のノードが画面外へ見切れてしまい、頻繁なスクロール・縮小を強いられます。
* **第三者視点の指摘**:
  * 「MindMeisterと同じ感覚で左右放射状に描画すると、サイドパネルでは実用に耐えない可能性がある。」
* **事前対策（仕様追加）**:
  1. **サイドパネル専用レイアウトモードの導入**:
     * サイドパネル表示時は、中心から右側のみに伸びる**「右方向ツリー（Logic Chart / Right-side layout）」**をデフォルトとする。
  2. **自動フィット（Auto-Fit Zoom）**:
     * ノードを追加・選択した際、アクティブな領域が自動的に画面中央に収まるセンタリング・ズーム補正を実装する。

---

### 【問題点 2】サイドパネルが「閉じている時」の右クリック追加エラー
* **リスク内容**:
  * ユーザーがWebページでテキストを選択し、右クリック「マインドマップに追加」を実行した際、**もしサイドパネルがまだ開いていなかったらどうなるか？**
  * サイドパネル（DOM/JS）が存在しない場合、Service Workerから送信されたメッセージを受信する側がおらず、データが消失するかエラーになります。
* **第三者視点の指摘**:
  * 「サイドパネルが開いていない状態を前提にしたデータ受け渡し設計になっていない。」
* **事前対策（仕様追加）**:
  1. **ストレージ直接書き込み方式への変更**:
     * メッセージング（`chrome.runtime.sendMessage`）だけに頼るのではなく、Background Service Worker が直接 `chrome.storage.local` のツリーデータ（または未分類インボックス「Inbox」配列）に選択テキストを追記する。
  2. **サイドパネルの自動オープン**:
     * 右クリック実行時に `chrome.sidePanel.open({ windowId })` を呼び出し、サイドパネルを強制的に立ち上げる。

---

### 【問題点 3】サイドパネルとフルタブの「同時編集コンフリクト（先勝ち上書き）」
* **リスク内容**:
  * ユーザーがサイドパネルを開いたまま、新しいタブで「全画面フルタブ」も開き、両方でノードを編集した場合、最後の自動保存がもう片方の編集内容を上書き消去（データ先勝ち競合）してしまう危険があります。
* **第三者視点の指摘**:
  * 「Googleドキュメントのような高度なOT（Operational Transformation）やCRDTを組まない限り、複数画面での同時編集はデータ先祖返りのリスクが高い。」
* **事前対策（仕様追加）**:
  1. **アクティブ排他制御（タブ連動）**:
     * フルタブ画面を開いた場合、サイドパネル側には「全画面モードで編集中です（クリックしてサイドパネルを有効化）」というオーバーレイを表示し、編集権限を一方に限定する。
  2. **または `chrome.storage.onChanged` による即時リロード警告**:
     * 片方が保存されたら、他方のエディタへ即座に最新ツリーデータを再読込させる。

---

### 【問題点 4】`chrome.storage.local` の容量上限（画像埋め込み時）
* **リスク内容**:
  * `chrome.storage.local` のデフォルト容量は **10MB** です。
  * テキストのみのマインドマップであれば数万ノードでも10MBに達しませんが、将来的にWebページのスクリーンショットや画像をノードに貼り付けた場合、Base64文字列でストレージ上限エラー（QUOTA_BYTES）が発生します。
* **第三者視点の指摘**:
  * 「画像添付や大規模なマップを何十個も作ると、数ヶ月後に突然保存できなくなる。」
* **事前対策（仕様追加）**:
  1. `manifest.json` の permissions に **`"unlimitedStorage"`** を追加する。
  2. これによりローカルディスクが許す限り容量制限が無制限となり、データ溢れのリスクを完全に排除できる。

## 3. レビュー結果に基づく仕様反映チェックリスト

上記のレビュー指摘を受け、設計・実装計画に以下の対策が正式に反映されたことを確認します：

- [x] **レイアウト対策**: サイドパネル時は「右展開ツリーモード」を標準化
- [x] **メッセージング対策**: 右クリック取り込み時は `chrome.storage` への直接保存キューを併用
- [x] **同時編集対策**: フルタブ表示時はサイドパネル側に編集ロック/同期オーバーレイを配置
- [x] **容量対策**: `manifest.json` に `"unlimitedStorage"` 権限を最初から付与

以上の対策を組み込むことで、技術的・運用的な懸念は払拭され、極めて堅牢で実用的な拡張機能の開発が可能と判断します。
